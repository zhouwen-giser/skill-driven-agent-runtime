# Codex 自主执行工作法

## 1. 先证据、后抽象

优先完成可运行垂直链路：A2A → Goal → Skill → Workflow → MCP → Result → Evaluation。只有链路真实产生事件和数据后，才扩展运营控制台和自动演化。

## 2. 每个阶段的循环

```text
读取需求与现状
→ 更新 ExecPlan
→ 实现最小增量
→ 运行相关测试
→ 检查需求追踪缺口
→ 修复根因
→ 完整门禁
→ 更新证据与状态
```

## 3. 开源研究方式

- 克隆到仓库外的研究缓存或 `third_party/research/`（默认 gitignore）。
- 锁定 commit 后阅读具体模块和测试。
- 在 OSS Intake 中记录“采用概念、采用 API 形状、直接依赖、复制代码”四种不同级别。
- 优先重用正式 npm 包，不复制内部文件。
- 对参考项目写结论，不把其领域模型直接搬入本项目。

## 4. 建议的并行子任务

可使用独立工作树/子 Agent 并行：

- A2A SDK 兼容性和契约测试研究；
- MCP SDK 和 Mock Server；
- LangGraph 动态编译 Spike；
- 开源许可证和 UI 研究；
- 数据模型和迁移草案。

合并前由主线程统一领域模型和 ADR，避免并行分支各造一套类型。

## 5. Codex 的停止规则

- 测试失败：继续定位和修复，不宣称完成。
- 需求不明确：优先从原 DOCX、问答结论和 ADR 解释；无法解释才阻塞。
- SDK 缺口：先 Adapter/薄补丁/契约测试；只有长期维护合理时才 Fork。
- 环境缺少真实依赖：用 Mock 完成最大范围并明确证据等级。
- 预算达到：输出进度、证据、缺口、根因和下一动作，不把预算终止标记为完成。
