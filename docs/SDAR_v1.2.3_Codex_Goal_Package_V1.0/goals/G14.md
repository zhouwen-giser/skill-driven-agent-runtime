## 必须完成的实施任务

1. 以 Decorator 包装基础 `UserGoalPlanningService`，不改写基础 Planner 权威。
2. 构建 Task Type、Capability Experience 和 Planning Heuristic Context。
3. 支持 off、shadow、advisory、active 四种 Injection Mode。
4. 经验增强 Plan 先经完整 Validator。
5. 被拒绝时最多一次无经验有界重规划。
6. Experience Repository/Timeout/冲突/低置信度时 fail-open 到基础 Planner。
7. 保存使用了什么、影响哪些 Skill Goal、用户是否接受、Validator/Outcome 结果。
8. 不允许经验修改用户 Contract、安全策略、Readiness 或 Terminal。

## 实施细则

- 先审计当前仓库符号和测试，禁止创建重复服务或第二权威；
- 所有新 Domain 对象必须有 factory/validator、immutable snapshot 和明确 error code；
- 所有模型输出必须使用 Zod/JSON Schema，并由确定性 Application 代码校验；
- PostgreSQL 写入必须定义事务、CAS/幂等和重启语义；
- Redis/BullMQ 数据必须可由 PostgreSQL 重建；
- 适合时先加入失败测试，再完成实现；
- 更新 OpenAPI、Acceptance Map、Architecture、Migration 和 Console（如本 Goal 涉及）；
- 不允许 TODO、空实现、仅接口或只在测试环境生效的产品路径。

## 禁止事项

- 不改写 v1.2.2 Goal/Skill/Outcome/Recovery Authority；
- 不让 LLM 直接写权威状态；
- 不保存私有思维链；
- 不引入 Python Sidecar 或文件型知识权威；
- 不让 Candidate 绕过 Promotion；
- 不自动发布 Skill；
- 不删除失败测试或降低冻结验收标准；
- 不修改与本 Goal 无关的功能，除非为修复真实架构阻断并记录 ADR。

## 验证

- 无经验和 Experience DB 故障时基础 Planner 正常。
- 经验 Plan 无效时回退成功。
- Shadow 不影响正式 Task。
- Advisory 必须人工确认。
- Usage Record 可关联最终 Outcome 和反例。

最低还必须运行受影响范围的 format、lint、typecheck、unit、contract、integration 和 build；最终完整 `pnpm verify` 在 G17 执行。
