# SDAR v1.3 Incident Runbook

Status: `PLAN_ONLY_OWNER_UNASSIGNED`

## Authorization boundary

This runbook prepares evidence and human decisions. It does not automatically
rollback, delete, restart, scale, rotate a credential, disable a Provider,
change a Feature Flag/Kill Switch, approve an Artifact or operate a database.
Every production mutation requires the named incident commander and the
specific operations or rollback owner.

## Severity proposal

- **SEV-0:** safety boundary, cross-tenant access or repeated physical effect.
- **SEV-1:** formal runtime unavailable, active-state corruption or credential
  exposure.
- **SEV-2:** major degradation, sustained fallback or deadline regression.
- **SEV-3:** limited degradation, queue lag, drift or cost anomaly.
- **SEV-4:** informational improvement opportunity.

The organization-approved incident policy supersedes these proposed labels.

## Required incident record

Record start, detection, acknowledgement, mitigation and resolution times;
environment; authorized tenant scope; exact Artifact and Provider references;
formal Outcome references; user/data impact; immutable evidence locations;
actor, approval and command identifiers; recovery checks; root cause and
follow-up. Reports must redact credentials, private prompts and unauthorized
tenant or PII fields.

## Common response flow

1. Acknowledge and assign incident commander, operations owner, rollback owner
   and security owner as applicable.
2. Preserve the deployment manifest, release SHA, configuration hash,
   migration ledger, active pointers, Outbox range and first bad event.
3. Establish scope from PostgreSQL-authoritative facts before relying on a
   dashboard aggregate.
4. Select containment from the approved rollback runbook. Do not improvise a
   destructive data operation.
5. Verify formal Goal/Plan/Attempt/Outcome integrity and absence of duplicate
   provider effects.
6. Communicate impact without secrets, private reasoning or unauthorized
   tenant details.
7. Resolve only after recovery conditions and an independent reviewer agree.
8. Create a postmortem and versioned backlog item; do not silently change
   v1.3.

## Runtime unavailable

- Check process readiness, PostgreSQL availability, migration ledger, pool
  saturation and formal Task admission.
- Preserve Cognitive Fallback if the compiled path is involved.
- Recovery requires an approved request-success window and authoritative Task
  state consistency.

## Security or tenant boundary

- Treat one confirmed cross-tenant access, actor spoof or credential exposure
  as immediate escalation.
- Stop exports and preserve audit evidence; never paste credentials or raw PII
  into the incident record.
- Credential rotation or access revocation requires the security owner and a
  separate approved procedure.

## Duplicate side effect

- Freeze the affected provider operation and exact idempotency key.
- Reconcile provider evidence with Formal Plan/Attempt/Outcome facts.
- Do not replay or delete facts to hide a duplicate.

## Queue or Outbox lag

- Compare PostgreSQL durable availability/sequence with BullMQ wake state.
- Check lease fencing, consumer cursor and oldest unpublished event.
- Redis may be rebuilt only after approval; PostgreSQL facts are never derived
  from Redis.

## Datastore degradation

- PostgreSQL: preserve connection, lock, disk and ledger evidence; do not run
  an unreviewed downgrade or data deletion.
- Redis: confirm formal runtime facts remain in PostgreSQL, then use the
  approved recovery plan to rebuild ephemeral state.

## Provider or Model Route

- Check Provider Registry/readiness, circuit state, classification/residency
  policy, token and cost budget, timeout and cascade depth.
- Disabling a Provider or Model Route is a named-owner action, not an alert
  side effect.

## Artifact quality regression

- Pin analysis to exact `artifactId:version`, pointer lock version, cohort and
  formal outcomes.
- Allowed recommendations are continue, collect more data, request
  revalidation, disable the fast path or open a next-version candidate.
- P14 never edits Artifact status.

## Cost or capacity anomaly

- Separate Fast Path, Cognitive Fallback, cascade, shadow, replay, compiler,
  management and incident costs.
- Never remove validation, tenant, confirmation or policy checks solely to
  reduce cost.

## Current blocker
