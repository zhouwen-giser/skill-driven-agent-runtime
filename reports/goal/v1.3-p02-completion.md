## Outcome

P02 establishes PostgreSQL as the sole durable Artifact, Approval, Active Pointer and governance
authority. Migration 0125 creates the ten exact frozen tables; repositories preserve the complete
P01 Artifact, Lineage and optional Runtime Binding, enforce immutable versions and Lineage, and
provide transactional validation, approval, activation, execution, feedback, audit and Outbox
evidence.

The Registry is a rebuildable, non-authoritative projection. Startup performs a real PostgreSQL
rebuild and drains only projection lifecycle/dependency events through a consumer-private CAS cursor.
Relevant event inserts acquire a transaction-scoped advisory lock before cursor allocation, so late
timestamps and concurrent reverse-commit attempts cannot create a skipped event. The projection
never mutates shared `published_at`.

G04 supplies fail-closed identity, explicit permissions, trusted tenant binding, complete request
idempotency, separate Approval/Activation, revalidation, deprecation, rollback and bounded kill
switch mechanics. It adds no public API, Console, online Artifact execution path, P03 compiler,
P05 replay engine, P06 promotion policy or second workflow runtime.

## Persistence and transaction design

- `compiled_artifact.definition` stores the bounded canonical P01 envelope; frozen relational fields
  are exact checked/indexed projections.
- Artifact content and Lineage rows are database-immutable. Projection drift, including creation
  time, fails closed.
- Activation locks the Artifact key, binds current passed Validation and latest matching approved
  evidence, checks tenant and expected versions, advances the Pointer tombstone CAS, changes status,
  records audit and writes Outbox in one PostgreSQL transaction.
- Deprecation and kill switch retain and increment the Pointer tombstone, preventing CAS ABA.
- Validation, Approval and Feedback events use per-run/decision/feedback aggregate identities, so
  repeated lifecycle cycles cannot collide.
- Relevant projection events receive commit-visible cursor values under a database trigger; the
  consumer advances only `cognitive_runtime_consumer_cursor`.
