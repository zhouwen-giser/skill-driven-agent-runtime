# SDAR v1.3 Release Rollback Plan

Status: `PLAN_AND_LOCAL_DRILL_EVIDENCE`

This plan preserves PostgreSQL authority and the existing cognitive fallback.
It is executed only by named operators during an authorized release. P13 runs
local synthetic drills but performs no production rollback.

## Trigger

The operations owner freezes rollout immediately when a stop condition in the
rollout plan fires. The rollback owner records the affected tenant, Artifact
reference, active pointer, application build, migration ledger head, first bad
event sequence and exact start time before changing controls.

## Ordered response

1. Set `SDAR_V13_FAST_GATEWAY_ENABLED=false`.
2. Set `SDAR_V13_MODEL_ROUTE_ENABLED=false` and
   `SDAR_V13_MODEL_CASCADE_ENABLED=false` if a Model path is involved.
3. Remove the affected `artifactId:version` from
   `SDAR_V13_ARTIFACT_ALLOWLIST`.
4. Disable the affected Artifact type flag.
5. Set `SDAR_V13_RETRIEVAL_ENABLED=false`; if isolation is uncertain, set
   `SDAR_V13_ARTIFACT_MODE=off`.
6. Invalidate rebuildable retrieval/cache projections.
7. If an approved predecessor exists, invoke the P06 formal Artifact rollback
   command with operator identity, reason, expected pointer version and an
   idempotency key.
8. Confirm the single PostgreSQL active pointer, governance audit record and
   corresponding Outbox event before reopening any compiled path.
9. Preserve the existing cognitive/base planner as the execution path.
10. If the application itself is faulty, redeploy the last approved immutable
    application build while retaining compatible PostgreSQL facts.

## Data and migration policy

- Do not delete Artifact, validation, lineage, usage, feedback or audit facts
  to make rollback appear clean.
- Redis, BullMQ and in-memory projections may be flushed and rebuilt from
  PostgreSQL.
- Released data-bearing migrations are not mechanically downgraded when doing
  so could discard or reinterpret facts. Apply a reviewed forward fix.
- A development-only down migration may be used only on an isolated disposable
  database after its guard confirms that data is expendable.
- An interrupted migration must leave neither a partial schema change nor a
  false ledger/checksum record. The normal migration is then reapplied.

## Verification after rollback

- the formal Goal/Plan/Attempt/Outcome chain is unchanged;
- no physical provider operation is replayed;
- the affected compiled path is not selected;
- the base cognitive planner remains available;
- active-pointer and Artifact definition rows agree;
- Redis projection rebuild produces the PostgreSQL-authoritative result;
- queued duplicate wakes coalesce and Outbox consumers remain idempotent;
- Management, SSE and A2A show the authoritative post-rollback state;
- audit evidence includes actor, reason, expected version and request identity.

## Escalation

Do not re-enable a path until the root cause, impacted fact range, recovery
evidence and corrective release have independent review. Cross-tenant access,
credential exposure, data loss, duplicate physical side effects, migration
corruption or an ineffective kill switch requires a new release-candidate
decision rather than a waiver.
