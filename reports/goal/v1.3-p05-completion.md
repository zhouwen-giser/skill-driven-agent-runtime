## G09 Source Inventory

The production `PostgresCognitiveRuntimeFactReader` and `GoalExperienceEpisodeBuilder` project
historical Request, Goal Contract, Plan, Attempt, Trace, Outcome, correction/recovery, Policy,
Readiness, Task Understanding and Capability Summary facts into immutable Episodes. Capability
authority follows the exact `generic_task_understanding.sourceRefs` entry to
`runtime_capability_summary` by summary ID, revision and catalog hash. It does not scan mutable
current Skill versions.

The real PostgreSQL regression persists terminal facts, disables every current Skill, and then
builds five production Episodes with five historical Capability Summary sources and twenty
historically ready capabilities. A missing or mismatched historical authority omits the snapshot;
current state is never fabricated.

## ReplayCase Contract

`ArtifactReplayCase V1.1` is a strict, deeply immutable 19-field contract with canonical content
hashing. It carries tenant, request, Goal Contract, Capability Catalog, world, policy, readiness,
accepted Plan, Trace, Outcome, correction, environment/device/task-type, Episode, lineage and
snapshot-completeness facts. Unknown fields, unbounded values and incomplete identities fail at the
Domain boundary.

## Snapshot Completeness

Completeness is derived from required versus available historical snapshot references. Missing
history remains explicit and makes the Case ineligible for promotion holdout. Production builders
do not use a test-only `replayValidation` field and do not substitute current Policy, Readiness,
Catalog, world or Outcome state.

## Dataset Split / Leakage Guard

`ReplayDatasetManifest V1.1` is append-only and versioned. The builder separates `discovery`,
`candidate_development`, `promotion_holdout` and `counterexample` purposes. Tenant, Goal lineage,
Episode/revision, accepted Plan revision, Outcome, request fingerprint, near duplicate, fixture
seed, environment, device and five-minute time windows are independent leakage axes. Candidate
source traces and incomplete Cases cannot enter promotion holdout.

The real product-chain evidence persists eight Cases across four Dataset purposes with three
independent promotion-holdout results and zero Candidate-source Cases in holdout.

## No-Physical Provider

Replay uses `executionMode=replay`, isolated ID/queue/telemetry namespaces and a snapshot-only
adapter. Credential, network, MCP, Provider Task, device control, external/formal writes, Active
Pointer writes and Remote Task control fail before a physical boundary. A real denied network
operation persisted one critical `side_effect_attempt`, one Counterexample and an `unsafe` Result;
the observed physical-call count is zero.

## Dataset Persistence / Worker

PostgreSQL is authoritative for Cases, Dataset versions, membership, Runs, Case Results, metric
samples, Failures, Counterexamples, leases, fencing, retry, cancellation, deletion tombstones and
terminal audit facts. Redis carries only `validationRunId` wakes.

Migration `0129_v13_artifact_replay_validation` extends P02's canonical
`artifact_validation_run`; it does not create a competing run authority. Idempotent claims,
stale-token rejection, bounded retry/dead-letter, cancellation and Redis loss/rebuild were
exercised. Four actual BullMQ workers completed twelve runs and the bounded four-claimer test
claimed 100 runs without exceeding 25 per claimer.

## G10 Plan Replay

Plan Replay materializes a non-persisted plan view from the P04 Candidate and reuses the existing
`validateUserGoalPlan`. It evaluates Goal criteria, evidence/artifact requirements, policy,
capability, readiness, parameters and recovery structure without creating a formal Goal, Plan,
Attempt, Workflow or LangGraph execution.

## Rule Replay

Rule evaluation preserves authority allow/deny/require-confirmation semantics, unknown/conflict
states, policy overrides, false-positive/false-negative evidence, missed confirmations and unsafe
allows. Any unsafe allow count above zero makes the complete Result `unsafe`.

## Counterfactual Replay

Counterfactual evaluation reports bounded structural differences in criteria, risk, nodes,
recovery, model/token and human-interaction facts. Physical Outcome remains `unknown`; P05 never
claims that an unexecuted physical action succeeded.

## Metric Catalog

The versioned catalog contains 29 transparent metrics. Each definition declares unit, direction,
denominator, aggregation, null policy, minimum sample and confidence rule where applicable.
Execution applies ratio numerators/denominators, P95 latency, independent-holdout generalization and
minimum-sample rules. No opaque aggregate validation score exists.

## Validation Result / Failure

`ArtifactValidationResult V1.1` freezes artifact, Dataset, validator and metric-catalog hashes.
Result identity is independent of run/failure/counterexample identifiers but changes with semantic
failure facts. Terminal Results/Runs are immutable. `unsafe_allow_count`,
`side_effect_attempt_count` or a critical safety failure forces `unsafe=true` and `result=unsafe`.
Candidate definition and lifecycle status remain unchanged; the terminal transaction emits only
`artifact.validation_completed`.

## Counterexample

Counterexamples retain artifact, Case, Failure, condition fingerprint, environment, failure-boundary
candidate and source lineage. Negative regressions cover missing parameter/capability/readiness,
authority deny versus Candidate allow, and a physically denied network operation.

## Reproducibility

Dataset and Result identities use canonical SHA-256 over frozen inputs. Duplicate triggers reuse
the immutable Run, exact Case multisets are enforced, stale Artifact/Dataset pins fail before
evaluation, and a lost Redis wake is rebuilt from PostgreSQL. User/tenant deletion invalidates
promotion eligibility and creates successor Dataset versions while retaining terminal audit facts.

## Failed Attempts

1. The first targeted integration used a shared database with an incompatible migration ledger.
   The rerun used an isolated clean-baseline database.
2. The first native product-chain run lacked enough holdout groups because fixture tenants differed.
   Aligning the Candidate to trusted-intranet tenant authority produced five production holdouts.
3. A terminal-run trigger initially guarded legacy P02 rows. Restricting it to pinned P05 Replay
   rows restored P02 compatibility; integration passed 109/109.
4. Production capability projection initially read mutable current Skill versions. Exact
   Understanding-to-Summary pins plus the post-fact Skill-disable regression closed the finding.
5. The first aggregate `pnpm verify` passed all product tests but the final infra smoke found no
   baseline marker in the pre-existing default `/sdar` volume. The default database was preserved;
   an isolated guarded `sdar_v122_p05_full_verify` database passed smoke and the complete rerun.
