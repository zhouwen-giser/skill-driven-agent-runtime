# SDAR v1.2.3 to v1.3 Upgrade Report

Status is taken from the latest
`reports/goal/v1.3-final-migration-report.json`. This document describes the
tested path and its operational interpretation.

## Supported source

The only release upgrade source in this audit is the exact
`v1.2.3-final` baseline commit
`856f909d22c33e6e20d7e0a1cffc2f54c03b4477`. The verifier applies the
v1.2.2 clean baseline plus the v1.2.3 migration prefix through `0124`, inserts a
representative v1.2.3 fact set, and then invokes the same
`applyRuntimeMigrations` implementation used by the standard Server.

The representative snapshot includes:

- a formal Goal and User Goal Plan;
- a Skill Goal/Attempt and Outcome decision;
- a completed Experience Episode with tenant/user scope;
- a Model Provider record with an opaque verifier credential envelope;
- an A2A Task projection.

The pre-upgrade and post-upgrade JSON snapshots must be byte-equivalent for the
selected authority fields. A missing row or changed value fails the command.

## Container image transition

The hardened candidate changes the PostgreSQL userspace from the exact
v1.2.3 Debian/glibc image to Alpine/musl. Reusing a Debian-initialized physical
`PGDATA` under the Alpine image is not a supported upgrade path. The retained
first failure from an earlier long-lived Debian volume was:

```text
template database "template1" has a collation version, but no actual collation version could be determined
```

The verifier therefore does not start or mount the existing `sdar` Compose
volume. It creates uniquely named source and target containers and volumes,
builds the exact v1.2.3 migration prefix and representative facts in
`pgvector/pgvector@sha256:69573b32242ca232f65871d4cb916ba7210a372b9bd74068204c1a9a57bada4f`
(PostgreSQL 17.10 on Debian 13 Trixie), the exact Compose pin at commit
`856f909d22c33e6e20d7e0a1cffc2f54c03b4477`. It then takes a custom-format
logical backup and restores it in one transaction into the repository-owned
hardened Alpine image. Only then does it apply the v1.3 migrations. No
substitute Debian fixture is accepted as v1.2.3 release-upgrade evidence.

The machine report records both OS identities, server versions, database
collations, archive SHA-256, exact image IDs, representative fact snapshot and
temporary-resource cleanup. No production data is used.

## Candidate migration range

- v1.2.3 prefix: `0108_v123_cognitive_skeleton` through
  `0124_v123_replay_shadow_evidence`
- v1.3 additive range: `0125_v13_artifact_authority` through
  `0134_v13_artifact_management_projection`
- expected final marker:
  `0134_v13_artifact_management_projection`

The verifier also exercises:

- empty-database application and idempotent reapplication;
- complete post-baseline rollback followed by reapplication;
- rejection of an existing unowned database;
- development reset environment and database-name guards;
- rejection of an unknown migration ledger entry;
- a deliberate interruption inside migration `0125`, transaction rollback and
  normal reapplication;
- SHA-256 drift rejection through a verifier-only checksum sidecar.

Released migration SQL is not rewritten by the checksum verifier.

## Rollback interpretation

The down/reapply exercise proves the repository's isolated development
migration path. It is not authorization to destructively downgrade a production
database. After v1.3 data exists, an incompatible change is handled by disabling
the affected runtime path and applying a reviewed forward fix that preserves
facts and version semantics.

## Deployment procedure

An authorized deployment must:

1. stop application writes, snapshot the source database and record the current
   ledger head;
2. verify the source is the supported v1.2.3 head and retain its physical volume
   unchanged for rollback;
3. take a verified logical backup from the source image; never mount its
   physical `PGDATA` in the Alpine image;
4. initialize a new Alpine volume and restore the logical backup in one
   transaction;
5. deploy the exact immutable candidate with compiled paths disabled;
6. apply migrations once through the standard Server migration entrypoint;
7. verify marker order, required constraints and representative read paths
   before retiring the source volume;
8. keep Redis projections disposable and rebuild them from PostgreSQL;
9. run health, Management, A2A and cognitive fallback smoke checks before any
   Artifact allowlist is populated.

No production database or production deployment was used by P13.
