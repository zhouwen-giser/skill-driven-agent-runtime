## Deterministic Rule Runtime

`DecisionRuleRuntimeService` evaluates only a P07-selected active
`decision_rule`. The immutable context pins Rule/hash/pointer, tenant,
Goal/Plan versions, request/world/business-event/binding/readiness/policy/
dependency references, authorization and a canonical runtime snapshot hash.
Current state is loaded before evaluation, after evaluation and immediately
before formal handoff.

The strict `runtimeDsl` uses typed operands, 18 operators, `all`/`any`/`not`,
explicit three-valued logic and recursive depth/string/collection bounds. It
contains no dynamic code, model operator or arbitrary network/database/file
operation. Same Rule/runtime/evaluator inputs have the same result hash.

Unknown never becomes true. Required unknown follows only a validated
no-match/fallback/confirmation policy; forbidden true denies; forbidden
unknown and confirmation unknown require confirmation.

## Policy, Conflict and Planning Authority

Existing policy and authorization ports are higher authority than Rule output.
Missing/stale/cross-tenant authorization, policy/hash drift, catalog/readiness
drift or kill switch fails closed. Request actor claims are not authority.

Conflict order is policy, deny, confirmation, specificity, explicit priority,
Artifact version and stable Rule ID. Compatible combination requires disjoint
groups/parameters/patch targets; ambiguity falls back.

Parameter suggestions must be low-risk, confirmation-bound and
non-authoritative. Plan patches may only add a constraint to an existing Skill
Goal or add a confirmation gate. They cannot change Goal, criterion, scope,
effects, evidence, authorization or human gates. The existing
`UserGoalPlanCandidateValidator` and P08 interactive planning session remain
the only formal authority.
