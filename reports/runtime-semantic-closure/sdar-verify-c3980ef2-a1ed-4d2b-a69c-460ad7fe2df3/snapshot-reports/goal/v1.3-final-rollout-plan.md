# SDAR v1.3 Release Rollout Plan

Status: `PLAN_ONLY_NO_DEPLOYMENT_AUTHORIZATION`

P13 defines the controls and stop conditions for a later authorized release.
It does not select a production environment, approve a release window, change
production configuration or deploy the candidate.

## Feature control matrix

All additive P13 controls default to disabled. An empty tenant or Artifact
allowlist never broadens an explicitly scoped rollout; the exact versioned
Artifact allowlist is empty-deny-all.

| Layer | Control | Initial value | Purpose |
| --- | --- | --- | --- |
| Global Artifact mode | `SDAR_V13_ARTIFACT_MODE` | `off` | disables compiled runtime selection |
| Compiler | `SDAR_V13_COMPILER_ENABLED` | `false` | disables P03/P04 durable compilation |
| Registry | `SDAR_V13_REGISTRY_ENABLED` | `false` | disables Artifact registry projection consumption |
| Shadow | `SDAR_V13_SHADOW_ENABLED` | `false` | disables shadow/revalidation workers |
| Promotion | `SDAR_V13_PROMOTION_ENABLED` | `false` | disables promotion packages and management approval/rejection/activation |
| Retrieval | `SDAR_V13_RETRIEVAL_ENABLED` | `false` | disables P07 selection before repository reads |
| Template | `SDAR_V13_TEMPLATE_ENABLED` | `false` | disables Plan Template materialization |
| Rule | `SDAR_V13_RULE_ENABLED` | `false` | disables Decision Rule path |
| Fast gateway | `SDAR_V13_FAST_GATEWAY_ENABLED` | `false` | disables P10 compiled orchestration |
| Case | `SDAR_V13_CASE_ENABLED` | `false` | disables Case Template path |
| Model cascade | `SDAR_V13_MODEL_CASCADE_ENABLED` | `false` | disables cascade selection |
| Model route | `SDAR_V13_MODEL_ROUTE_ENABLED` | `false` | independently disables Model Route artifacts |
| Tenant scope | `SDAR_V13_TENANT_ALLOWLIST` | empty | limits enabled paths to named tenants |
| Artifact scope | `SDAR_V13_ARTIFACT_ALLOWLIST` | empty | allows exact `artifactId:version` references only |

## Staged activation

Each phase requires an authorized operator, a frozen configuration snapshot,
the named monitoring dashboard/query set, a rollback owner and a successful
checkpoint before advancing.

1. **Disabled.** Deploy application and migration compatibility only. Keep
   `ARTIFACT_MODE=off` and every additive flag false.
2. **Compiler/replay only.** Enable compiler and registry for durable candidate
   evidence. Keep retrieval, promotion and runtime paths disabled.
3. **Shadow only.** Enable replay, shadow and revalidation for approved
   datasets. Keep active runtime retrieval disabled.
4. **Internal tenant.** Add one non-production/internal tenant to the tenant
   allowlist. Keep the exact Artifact allowlist empty until validation and
   approval evidence is reviewed.
5. **Low-risk Artifact.** Add one approved low-risk exact Artifact version.
   Enable only its type-specific runtime flag and retain formal confirmation.
6. **Limited canary.** Enable the fast path for a bounded tenant/request share
   at an operator-defined release window.
7. **Broader rollout.** Expand tenant and Artifact allowlists one bounded step
   at a time. Model routing is a separate decision and remains off unless its
   provider, budget and privacy gates are approved.

No phase is time-triggered. Lack of evidence means remain at the current phase.
Deprecation, rollback and kill-switch commands remain authenticated,
permission-checked emergency controls even when promotion and shadow are
disabled.

## Canary observation

The operations owner must compare canary and control cohorts using
PostgreSQL-authoritative evidence for:

- authorization, policy and cross-tenant denials;
- unsafe or rejected validation;
- Goal outcome and correction regression;
- confirmation frequency and operator override;
- deadline expiry, cancellation and late-result discard;
- compiled-path fallback and fallback failure;
- p95/p99 latency, queue lag and Outbox age;
- duplicate event or physical side-effect evidence;
- active-pointer and cache projection agreement;
- model invocation cost, token budget and cascade depth;
- Artifact match, execution, feedback and drift.

Local P13 capacity measurements establish a repeatable engineering baseline.
Production thresholds must be supplied and approved by the named operations
owner; P13 does not invent them.

## Immediate stop conditions

Any of the following stops advancement and begins rollback:

- credential, sensitive prompt or private reasoning exposure;
- cross-tenant/IDOR access or actor spoofing;
- unapproved Artifact activation or active-pointer corruption;
- duplicate formal Goal, Plan, Attempt, terminal Outcome or physical side effect;
- unsafe rule/template/case/model output crossing formal validation;
- statistically or operationally material outcome regression;
- deadline, queue or database saturation that threatens the formal runtime;
- loss of PostgreSQL facts or inability to rebuild Redis projections;
- failed kill switch, cognitive fallback or rollback drill;
- Critical/High dependency or container vulnerability in the shipped graph.

## Authorization boundary

P13 authorizes none of merge, tag, release or deployment. The release manifest,
target environment, deployment and monitoring access, release owner, operations
owner and rollback owner are P14 inputs and must be explicit before production
work begins.
