## Runtime, Materialization and Safety

`TemplateRuntimeService` accepts only the P07 `template_adapt` decision for
the selected active `plan_template`. It re-reads the P02 definition and active
pointer and checks version, hash and pointer lock. It then checks the current
Goal/contract, matcher and policy snapshots, capability-catalog hash, readiness
hash and kill switch both before materialization and immediately before formal
session admission. Any change returns `discarded_stale`; a kill switch returns
`deny`.

Only P07 `ParameterBindingResult` values are rendered. Source, trust and schema
are checked against the immutable template parameter declaration. Missing
required values require confirmation; a candidate value cannot be promoted, and
an unpermitted source falls back. No P08 model call fills a parameter.

Materialized nodes retain objectives, capabilities, effects, criterion coverage,
evidence, artifacts, inputs, constraints, parallel groups, optional conditional
edges and recovery branches. A materialized candidate has no exact Skill,
Provider, MCP or Workflow binding. Required Goal criteria, evidence and artifact
requirements are added rather than weakened; unsafe recovery replay is rejected.

## Formal Authority and Durable Correlation

P08 uses `UserGoalPlanCandidateValidator`,
`InteractivePlanningSessionService.startWithMaterializedCandidate` and the
existing `ConfirmedPlanHandoff` / Goal-version lock / `UserGoalPlanningService`
chain. The small new session seam does not duplicate the validator, state
machine or formal plan persistence. A stable idempotency-derived instantiation,
execution, candidate and plan identity prevents duplicate formal handoff; a
different candidate for the same task is rejected.

P02 `ArtifactExecutionRepository` records the instantiation and P02 feedback
correlates stale or handoff results. These are usage facts only: P08 neither
copies formal outcomes nor creates Skill Attempts, Workflows, executions or
recovery actions. Redis owns neither Candidate nor Run authority.

## Server Composition and Scope

The Server composition root exposes the internal runtime only when the
deployment supplies a `TemplateRuntimeStateReader`. No HTTP, Management, A2A,
Fast Gateway, Rule, Case or Model Runtime route was added. The internal runtime
does not call Skill, Provider or MCP operations.

The infrastructure and server smoke checks now use a created-and-dropped
temporary database, preserving the operator's local `sdar` database while
testing a clean baseline/migration path. This corrects a reproducible smoke
environment-drift failure without changing production persistence authority.
