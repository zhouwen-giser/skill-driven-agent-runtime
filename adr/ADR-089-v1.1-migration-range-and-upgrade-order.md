# ADR-089: v1.1 Migration Range and Upgrade Order

## Status

Accepted on 2026-07-16.

## Context

The v1.1 task package reserves migrations `0100+` so parallel development does not edit the hardening branch's `0057+` files. The current monotonic migration runner uses the greatest applied four-digit sequence as a high-water mark. If `0100` is applied before future `0057`–`0099`, those later migrations would be skipped.

## Decision

- Released migrations `0001`–`0056` remain immutable.
- v1.1 files use `0100+`, but before `v1.0.13-bug-fixed` they may run only in disposable, explicitly isolated v1.1 development databases.
- The supported install/upgrade chain is the complete published v1.0.13 ledger followed by `0100+` in filename order.
- When new hardening migrations are merged, rebuild disposable v1.1 databases rather than marking skipped history as applied.
- Phase 6 migration tests must prove empty install and upgrade from the exact v1.0.13-bug-fixed schema. Release checks reject any ledger gap or `0100` preceding an unapplied lower released migration.

## Consequences

Parallel schema work can proceed without filename collisions, while no production-like database is placed into an unrecoverable high-water state. Final release remains blocked on the complete hardening chain.

Phase 2 implements this decision with an explicit `v1.1-isolated` migration profile. It requires both an acknowledgement and a disposable `sdar_v11_*` database name; the default profile neither applies `0100` nor accepts a database that already contains the reserved range. `scripts/verify-v11-migration-path.mjs` proves empty, released-0056 upgrade, rollback/reapply and fail-closed paths.

## Rejected Alternatives

- Allocate current next numbers on both branches: creates merge collisions.
- Change historical migration filenames: breaks released evidence.
- Teach the runner to fill arbitrary gaps during Phase 0: broadens migration semantics during a parallel release and requires an independent migration-hardening project.
