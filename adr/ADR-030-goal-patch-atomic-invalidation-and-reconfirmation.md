# ADR-030: Goal Patch atomic invalidation and reconfirmation

## Status

Accepted on 2026-07-12.

## Decision

- A Goal Patch is generated by the fixed `goal` model stage as validated data. It may change only title, description, constraints, and success criteria; it cannot provide executable source or mutate a running graph.
- One PostgreSQL transaction locks the active Goal, increments its version, invalidates every old-version plan and Workflow instance, clears old Task plan/result bindings, and persists immutable before/after and invalidation evidence.
- Invalidation commits before replanning. If model planning subsequently fails, old execution state stays invalid and cannot be revived.
- Replanning occurs outside LangGraph and creates a new immutable Workflow version. The new plan always starts `awaiting_confirmation`, even if every selected Skill normally permits automatic confirmation.
- Already completed side effects are never automatically undone. Skill compensation guidance is supplied to planning when available; direct MCP calls and missing guidance create visible warnings.

## Consequences

- Goal version is the authority boundary for plans, instances, Task results, and confirmations.
- A Patch cannot race a second Patch against the same version because the Goal row is locked and version-checked.
- Operators can reproduce the change from its instruction, structured model summary, before/after Goal, invalidated identities, warnings, and new plan identity.
- V1 makes side-effect uncertainty explicit instead of claiming transactional compensation across external systems.
