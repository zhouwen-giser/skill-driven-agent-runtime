# ADR-109: v1.2.2 Clean-slate User Goal Runtime and Terminal Authority

## Status

Accepted on 2026-07-22. This supersedes ADR-108 only where ADR-108 retains the `legacy_v11` product
path, and supersedes earlier Workflow/Goal-controller decisions wherever they allow Workflow completion
or the old Goal evaluator to commit the User Goal/A2A terminal state. Frozen MCP Tasks V1.0, adapter
isolation, immutable Workflow execution and PostgreSQL authority remain in force.

## Context

The v1.2.1 product plans a Workflow after Skill selection and supports explicit Legacy/Frozen MCP
Provider modes. The v1.2.2 frozen Goal instead requires a User Goal completion contract and Skill Goal
DAG before selection, independent Task/Skill/User outcome judgment, one terminal authority, bounded
recovery with no replay, and no Legacy product path or historical data migration.

Treating the Skill Goal DAG as another executable graph would violate the single LangGraph runtime.
Letting Workflow completion, Provider Task completion or a model decision directly finish A2A would
retain conflicting terminal authorities. Preserving Legacy projections would contradict the clean-slate
upgrade and keep untestable fallback semantics.

## Decision

- v1.2.2 has one product protocol mode: Frozen MCP Tasks V1.0. Remove `legacy_v11`, Legacy clients,
  transport routing/fallback, Legacy Skill Usage projection and their management/Console switches.
- The database is rebuilt from one v1.2.2 baseline. No historical runtime migration, Legacy projection
  or down migration is provided. Reset is restricted to explicit development/test databases.
- Domain owns immutable `UserGoalCompletionContract`, `UserGoalPlan`, `SkillGoal`, dependency,
  criterion coverage, `SkillOutcomeSpecification`, `SkillExecutionContract`, `SkillAttempt`, layered
  outcome, progress, budget, completed-effect and recovery records.
- A Skill Goal describes a required result and never names a Skill, Tool, Provider or Workflow. Skill
  selection starts only after the plan validator accepts a 100%-covered bounded acyclic DAG.
- The Skill Goal DAG is planning/scheduling data. It never compiles or executes as a graph runtime.
  Every Skill Attempt still creates an immutable Workflow plan and executes only through LangGraph.js.
- Application owns `UserGoalPlanningService`, `SkillGoalPlanValidator`, `SkillGoalScheduler`,
  compatibility admission, Task/Skill/User judges, `RecoveryCoordinator` and
  `UserGoalPlanController`.
- PostgreSQL owns `goalId + goalVersion` serialization/CAS, immutable plans/revisions/attempts/outcomes,
  dispatch uniqueness, budgets, completed effects and terminal authority. Redis carries only
  reconstructable work references.
- External model, MCP, HTTP and Queue calls are forbidden while the Goal lock/CAS transaction is held.
  A locked transaction may validate current state and create a dispatch intent; external work occurs
  after commit and returns through a new CAS operation.
- Provider Task completion and Workflow completion are observations only. Deterministic rules and
  validated semantic judgment produce separate Task Goal, Skill Goal and User Goal outcomes.
- Low confidence cannot produce `achieved` or `none`. Missing/ambiguous evidence fails closed to input,
  capability gap, recovery or human review.
- `UserGoalPlanController` and its PostgreSQL terminal transaction are the only authorities allowed to
  commit User Goal terminal state and its A2A projection. Workflow and old Goal controllers may publish
  attempt/outcome evidence but cannot write A2A terminal state.
- Goal Patch, recovery and event impact create a new immutable plan revision. They inherit validated
  completed effects/evidence/artifacts and forbid replay of already completed side effects.

## Consequences

The product intentionally breaks compatibility with historical databases, Legacy MCP Providers and
Legacy Skill projections. Existing Frozen MCP Tasks, continuation and exact version/evidence mechanisms
remain reusable behind new Skill Goal/Attempt links.

Architecture gates must reject Legacy symbols and terminal writes outside the single controller.
Acceptance must prove false-achieved cases, terminal races, scheduler races, lock/external-call
separation, restart budget persistence and no replay.

Business Events adds a separate strict adapter and durable client but cannot become a second Goal,
Workflow, terminal or state authority. Its impact decisions must enter the same recovery/controller
path.

## Rejected Alternatives

- Retain Legacy as a disabled mode: still leaves product code, schema and fallback semantics.
- Execute the Skill Goal DAG directly: creates a second workflow runtime.
- Let Workflow completion finish A2A: collapses layered outcomes and permits false achieved results.
- Hold a Goal lock while selecting a Skill or calling a Provider: couples database serialization to
  unbounded external work and creates deadlock/latency risk.
- Migrate historical runtime rows: conflicts with the frozen clean-slate development upgrade.
