## Purpose / Outcome

Deliver the Goal-to-Skill-to-existing-Workflow-to-MCP-Task usage chain defined in
`docs/24_V1_2_SKILL_DRIVEN_CAPABILITY_USAGE_DESIGN.md`, with immutable exact-version contracts,
three execution modes, bounded composition, Provider binding policy, plan compliance and queryable
execution/evidence records. Completion requires Phase 15 full verification and a Ready-for-Review PR;
this plan never authorizes merging the PR.

## Context and Orientation

- `packages/domain/src/skill.ts` owns `SkillVersion`; v1.2 extends it additively.
- `packages/domain/src/skill-graph.ts` owns immutable graph snapshots with generic depth 8, 32 related
  Skills and 128 relations. V1.2 adds a separate usage budget capped at 5.
- `packages/application/src/skill-registry.ts`, `skill-selection.ts`,
  `skill-semantic-retriever.ts` and `skill-composition.ts` are the existing catalog/discovery/graph path.
- `packages/application/src/workflow-planner.ts`, `workflow-validator.ts`,
  `workflow-controller.ts` and `skill-call-workflow.ts` are the only integration path.
- `packages/langgraph-runtime/src/workflow-compiler.ts` remains the sole runtime.
- V1.1 availability/timing, RemoteTaskBinding, persisted continuation, input/cancel/reconcile and
  restart recovery are merged into `main`; PostgreSQL remains authoritative and Redis ephemeral.

## Architecture and Interfaces

Domain owns the new immutable usage, package-neutral, applicability, interpretation, composition and
execution-record models. Application services coordinate existing repositories and services. JSON
Schema validation stays at the package/import boundary. Provider and Workflow status are referenced,
never copied. Procedure compilation outputs existing `WorkflowDefinition` data and does not execute.

Touched boundaries must preserve:

- no SDK/ORM/LangGraph types in Domain;
- no second runtime or mutable running graph;
- no LLM-generated executable source;
- no Tool/Task side effect before required confirmation;
- Goal Patch invalidates old usage/plan/workflow/intermediate authority;
- same-context serialization and v1.1 one-attempt/idempotent continuation;
- PostgreSQL as the only production source of truth.

Major Phase 6 decisions are recorded in ADR-097–103. Migrations were allocated only after the shared
v1.1 baseline was rechecked; Phase 11 applied high-water is now 0106.

## Discoveries and Surprises

- The supplied attachment contains the complete Goal task package but not the separately named Overall
  Design source. The exact supplied package is frozen; the normalized design explicitly discloses this.
- `gh` is unavailable, but the installed GitHub connector can read/create/update PRs. It confirms PR #4
  merged on 2026-07-17.
- `.env` is ignored and configures operator-managed infrastructure plus PostgreSQL port 54329. The
  repository migration verifier expects default 55432. A trap-isolated `.env` produced the valid
  self-managed Compose baseline without changing user configuration.
- `reports/v1.1-mcp-tasks/sync-state.json` is stale at Phase 4 despite final Phase 6 reports. V1.2 uses
  Git ancestry, PR metadata, source symbols and current verification rather than that stale field.
- Existing Skill graph and Skill call depth limits are 8. V1.2 cannot reuse them as its required hard 5.
- The safe package boundary needs no YAML parser: strict JSON machine files plus bounded UTF-8
  `SKILL.md` preserve deterministic validation and avoid a new dependency.
- The ignored operator `.env` conflict remains reproducible. The Phase 2 full gate used the same
  EXIT-trap isolation as Phase 0 and restored the file unchanged after all seven stages passed.
- A direct sandboxed all-contract invocation cannot bind loopback sockets and reported 73 `listen
EPERM` failures. The authorized Phase 5 full gate ran those contracts successfully; this is an
  environment restriction rather than a product regression.
- Phase 6 entry remained 0 behind current main. The branch was created from the already-integrated v1.1
  baseline, so the conditional merge path is intentionally not exercised and no empty merge is created.
- Phase 7 initially extended the isolated post-v1.1 migration chain through 0105 while preserving the
  released profile at 0064. Phase 10's production wiring proved that temporary pre-main posture could
  not remain after merge; ADR-106 now promotes the ordered chain while retaining isolated test guards.
- The first Phase 8 vertical exposed a strict composition snapshot parser that had not admitted the
  additive `usageSpecification`. The database boundary now admits that one field and the Domain
  revalidates the complete Usage contract; legal round-trip and corrupted-apiVersion rejection are
  covered by the real PostgreSQL suite.
- Phase 10 exposed that the PostgreSQL Skill-selection mapper stripped additive `usageSummary` and
  `usageCandidate` fields. Strict nested schemas now preserve and validate the exact evidence required
  by runtime planning; the original 22 E2E failures reduced to zero.
- Phase 10 also exposed two integration-boundary conflicts: duplicate in-graph confirmation would have
  competed with the authoritative outer plan confirmation, and the pre-main migration profile left the
  production Server unable to read 0105. ADR-105/106 preserve one confirmation and one monotonic schema.
- The operator-owned `sdar` volume has an historical `0064,0105` ledger gap. The new released runner
  correctly fails closed and no operator data was changed; clean verification used a disposable
  bootstrap database and removed it afterward.
- Phase 11's first complete PostgreSQL repository run exposed two historical tests that temporarily
  installed only 0100–0102 or rolled back 0055 beneath the now-released 0100–0106 chain. The tests now
  exercise the monotonic released profile, roll dependent migrations in reverse where required, and
  preserve v1.1 `cancel_observing` Provider-authority semantics; the complete suite passes 57/57.

- D10-009 / ADR-097–103: freeze exact versioned usage, three modes through the existing Workflow,
  normative authority, the shared recursive budget, package import authority, direct V1.1
  readiness/continuation reuse and a minimal execution-record boundary.
- D10-010: allocate append-only migration 0105 to Skill usage/import persistence and 0106 to execution
  records.
- D10-011 / ADR-096/097/101: persist Usage on existing `skill_version`, key import audit to the same
  exact version, and derive lifecycle from existing status. Package validation is read-only; production
  import re-reads/revalidates and atomically records the exact-next-version checksum snapshot.
- D10-012 / ADR-104: Task Type is the exact registered operation name, `serverId` remains Provider
  identity and hard attributes derive only from validated V1.1 Task semantics. Usage-aware selection is
  always wired; unavailable metadata yields zero candidates and cannot bypass readiness.
- D10-013 / ADR-105: all modes converge on the existing Workflow DSL/Validator. Template/procedure use
  deterministic data compilation; guidance uses bounded structured policy. Structural compliance is
  authoritative; natural-language normative/forbidden items remain immutable review data at the
  existing outer Workflow Plan confirmation, with no duplicate in-graph confirmation.
- D10-014 / ADR-106: now that v1.1 is merged into main, the default released migration profile advances
  through the ordered 0100–0105 chain. Disposable isolated-profile guards and ledger-gap rejection stay.
- D10-015: persist the validated Usage policy on the existing immutable Workflow definition and inherit
  it through bounded repair/replan/revision/Goal Patch. Legacy undeclared composition may use only the
  existing exact Skill Graph authority; native fixed/slot composition remains closed.
- D10-016 / ADR-103: store one immutable execution identity plus append-only ordered events and thin
  references. Status is derived from events and may only follow the Domain transition graph; Task,
  Workflow, remote Provider and terminal-outcome records remain authoritative. Runtime projection
  failures are structured warnings, never permission to rewrite an authoritative terminal state.

## Outcomes and Retrospective

Phase 0 established a clean, reproducible and remotely recoverable execution surface. Phase 1 froze the
usage contract, Phase 2 provides a fail-closed package boundary, Phase 7 makes the validated PostgreSQL
snapshot the exact-version production authority, and Phase 8 connects that immutable demand to live
Provider readiness without copying resource state. Phase 9 projects that decision into one bounded,
validated Workflow planning authority. Phase 10 connects that authority to the existing runtime and
confirmation path without a second graph or state machine. Phase 11 adds the narrow append-only
execution/evidence projection without a second lifecycle or telemetry platform. Draft PR #5 remains the long-lived
integration surface. The final outcome remains open;
`SDAR_V1_2_GOAL_COMPLETE` is forbidden until every Phase 15 condition passes.
