# EP-09 — SDAR v1.1 MCP Tasks

## Purpose / Outcome

Deliver the ordered Phase 0–6 upgrade defined by `docs/sdar_v1_1_mcp_tasks_codex_parallel_upgrade_package.md`. The result adds the official MCP Tasks extension contract behind the existing MCP adapter, durable provider-authoritative remote-task tracking, BullMQ polling, external-wait continuation, availability/time guards, input and cancellation handling, management observability, and final hardening integration without adding a workflow runtime or a new default DSL node.

The final Phase 6 gate may start only after `v1.0.13-bug-fixed` is published and merged. Until then, Phase 1–5 increments are development evidence and cannot be called the v1.1 release.

## Requirements Covered

`docs/22_V1_1_MCP_TASKS_DESIGN.md` owns the v1.1 addendum IDs `FR-MCPT-001`–`FR-MCPT-014`, `NFR-MCPT-001`–`NFR-MCPT-004`, and `AC-MCPT-01`–`AC-MCPT-16`. `docs/17_TRACEABILITY_MATRIX.md` records implementation, tests, commands, classification, and status without changing the V1.0 requirement baseline.

## Context and Orientation

- `packages/domain` owns remote-task, availability, observation, control and business-result models.
- `packages/application` owns protocol-neutral ports, scheduling, polling, reconciliation, continuation and lifecycle orchestration.
- `packages/mcp-adapter` alone maps official SDK/wire models. It uses exact `@modelcontextprotocol/client@2.0.0-beta.4` for extension-era negotiation and legacy fallback, plus locally validated frozen extension schemas. Exact `@modelcontextprotocol/sdk@1.29.0` remains only as the staged legacy loopback Server fixture; its experimental Tasks API is never authoritative.
- `packages/langgraph-runtime` remains the only Workflow runtime. It may return an external-wait signal and persist a continuation snapshot, but it does not hold a long-lived Promise or use LangGraph interrupt/resume for remote Tasks.
- PostgreSQL owns bindings, observations, controls, continuation snapshots and availability evidence. Redis/BullMQ schedules idempotent polling only.
- `packages/management-api` and `apps/console` expose real projections and actions without owning remote state.
- `apps/server` remains the single-process composition root.

## Architecture Invariants

1. The existing `mcp_tool` node is the default DSL surface; no `mcp_task` node is added unless later evidence and an accepted ADR require it.
2. A Tool call returns either a domain-owned synchronous result or a domain-owned remote-task acceptance. Unknown or malformed variants fail closed.
3. The MCP Provider owns remote status, result and admission. SDAR owns binding, local continuation, polling policy, audit and A2A projection.
4. `serverId` is the v1.1 provider authority identifier. `agentTaskId` and `remoteTaskId` are distinct fields.
5. A binding uses a stable `workflowNodeRunId`, not only a DSL node ID, so loop/repeated executions cannot alias.
6. Credential/session revisions are referenced, never persisted as plaintext in task records.
7. `waiting_external` is durable local state and is exempt from interrupted-running failure. Ordinary running/evaluating work retains the V1 non-recovery rule.
8. Remote control events resume a persisted continuation outside the old graph invocation; the immutable Workflow graph is never edited in flight.
9. Goal Patch, cancellation and confirmation invalidation rules continue to apply to every remote binding and pending control.
10. Poll attempts are idempotent, one-attempt BullMQ jobs. Transport retry is bounded and distinct from business elapsed-time terminal decisions.

## Discoveries and Surprises

- The required `tasks/get`, `tasks/update` and `tasks/cancel` surface is the official `io.modelcontextprotocol/tasks` extension at `modelcontextprotocol/ext-tasks`, not the legacy MCP 2025-11-25 experimental Tasks API exposed by SDK 1.29.0.
- The official extension is an Apache-2.0 incubation repository with no release tag or NOTICE. Phase 0 therefore pins commit `8966bea9c4f4e6d71060cc8284a539086e9e234f` and both schema blobs.
- The current migration runner treats the greatest four-digit filename as a high-water mark. Applying `0100` before future hardening migrations would silently skip `0057`–`0099`; Phase 1–5 may use `0100+` only in disposable isolated databases, and the supported path waits for the complete v1.0.13 chain.
- Current `McpRegistryService.call()` treats SDK `isError: true` as transport success. Phase 1 must normalize synchronous business errors explicitly rather than hiding them as successful results.
- The Phase 1 Spike proved that SDK 1.29.0 negotiates no protocol newer than `2025-11-25`, while the official extension forbids treating `2025-11-25` as extension-enabled. Its low-level request path therefore cannot implement this contract. Official split v2 beta.4 tags resolve to commit `e81758caed29f6568ce8873f7f9a3bd65b017d9c` and supply automatic modern discovery with legacy fallback.
- The official v2 beta currently identifies its modern fixture as `2026-07-28`, while the frozen extension draft identifies `2026-06-30`. Phase 1 records the negotiated revision and claims only the exact contract-tested beta/extension combination.
- Executable beta.4 Spikes showed that the Client codec rejects `resultType: task` before an explicit Schema and era-gates `tasks/get`/`tasks/cancel`; its transport also derives `Mcp-Name` from `name`, not `taskId`. ADR-090 confines a temporary alias/result/Header bridge to the adapter while preserving the exact external wire.
- Existing startup recovery fails every running Workflow. The exemption must be narrowly based on a durable active remote binding and cannot imply general Task crash recovery.
- Historical pre-convergence evidence used the then-terminal `0056_mcp_execution_mode` marker. After hardening convergence, the isolated guard verifies released terminal `0064_memory_production_hardening` and enforces `0064 → 0100 → 0101`; default-profile and ledger-gap cases fail closed.
- Provider `lastUpdatedAt` is the ordering authority. Namespaced revision/event metadata improves deduplication and traceability but cannot roll accepted state backward; a delayed older response is persisted as a rejected observation.
- The referenced filename `SDAR_v1.1_MCP_Tasks_升级方案.md` does not exist. The source package and byte-frozen `SDAR_v1.1_MCP_Tasks_升级设计文档.md` provide the corresponding design input; the canonical implementation design is `docs/22_V1_1_MCP_TASKS_DESIGN.md`.
- The model-facing Workflow JSON Schema previously allowed unknown node-specific fields because `additionalProperties` constraints were distributed across `allOf`. Phase 3 closes that hole with an object-level `unevaluatedProperties: false` contract and regression tests.
- A plan confirmation cannot authorize a later risk increase. Pre-call restricted execution now requires a matching restricted planning snapshot with no increased severity/effects, weaker reservation, earlier expiry or later earliest-start; otherwise it fails closed with a reconfirmation reason.
- A fresh LangGraph 1.4.7 invocation accepts `Command({ update, goto })` on a new thread and starts at the supplied frontier without invoking `START`. Native parallel barriers cannot carry predecessor arrivals across invocations, so Phase 4 persists compiler-owned join-arrival evidence and never treats a waiting node as a completed predecessor.
- Stable node-run ordinals and accumulated budget must be persisted; restoring only node IDs/outputs would alias repeated nodes and reset execution limits. A remote child wait must remain owned by the child Workflow and propagate through parent lineage rather than leaking the child's remote binding into the parent.
- The latest published hardening source at Phase 3 start remained `v1.0.4-bug-fixed` (`fa4b050` fetched state). No v1.0.5/v1.0.11 tag was available, so Phase 3 used narrow interfaces and did not refactor transitive Skill confirmation or generic Tool semantics.

## Implementation Steps

### Phase 0 — Design freeze

1. Record clean baseline, repository/symbol map and hardening overlap.
2. Freeze requirement and acceptance IDs, provider extension and architecture decisions.
3. Complete OSS Intake with exact licenses, commits and schema blobs.
4. Update project status, traceability, assumptions, ADR index, changelog and Phase reports.
5. Run the Phase 0 evidence gate, commit `docs(v1.1): freeze MCP Tasks upgrade baseline`, push, then record publication evidence without amending published history.

### Phase 1 — Protocol adapter

Add local wire schemas and domain-neutral result unions; implement `tools/call`, `tasks/get`, `tasks/update` and `tasks/cancel`, required `Mcp-Name`/`Mcp-Method` headers and capability negotiation. Reject unknown result discriminators, invalid transitions and `isError` ambiguity. Contract-test against a real loopback official-SDK transport.

### Phase 2 — Persistence and polling

Add forward migrations in the reserved v1.1 range, repositories, idempotent poll jobs, bounded backoff, lease/claim behavior, observations and startup reconciliation. Prove no duplicate control delivery and no resurrection of terminal/invalidated bindings.

### Phase 3 — Availability and time

Persist availability snapshots; add plan-time readiness, restricted-time risk decision and deterministic guards; repeat readiness immediately before invocation. Distinguish forecast, reservation, start window, maximum elapsed time, transport unreachability and business timeout.

### Phase 4 — External wait and continuation

Return a typed `waiting_external` result from the sole LangGraph executor, persist the continuation snapshot and terminate the active graph invocation. Route ordered control events through an idempotent inbox and resume only the affected node/branch outside the old invocation. Preserve child-Workflow lineage and confirmation/terminal consistency from the latest hardening merge.

### Phase 5 — Lifecycle outcomes

Map `input_required` to the existing Task input system without fresh Goal planning; send answers with `tasks/update`. Make cancellation requested/acknowledged/provider-terminal states distinct. Produce structured business outcomes for admission rejection, missed start, maximum elapsed, failed, cancelled and completed-with-error.

### Phase 6 — Integration and release

Merge published `v1.0.13-bug-fixed`, resolve overlaps preserving both suites, run all 16 AC scenarios and full gates/demos, complete API/operations/risk/release evidence, set version, tag and publish the final integration branch/PR.

## Idempotence and Recovery

- Never amend, rebase or force-push published phase commits.
- Never edit released migrations. Rebuild only disposable v1.1 development databases when hardening migration history advances.
- Duplicate poll/control delivery is expected and must converge through persisted identity/version checks.
- Provider unreachability retains the binding and schedules bounded observation retry. Only a Provider-returned `deadline_reached` business result may represent maximum elapsed; SDAR wall-clock, TTL or unreachability never produces that terminal remote state.
- Goal Patch or local terminal cancellation invalidates pending snapshots and causes later stale observations/controls to be audit-only.
- If hardening overlaps a touched semantic surface, stop only that phase, preserve the work, write the conflict report and resume after the required merge.

## Outcomes and Retrospective

Phase 1 established the protocol boundary without importing an SDK model into the domain or adding another runtime. The compatibility Spike invalidated the original v1 low-level-request assumption; ADR-090 now locks the exact official v2 beta client and constrains the smallest bridge to adapter internals while contract tests observe the unmodified external extension wire. Immediate business rejection is no longer audited as success, and legacy ordinary Tools retain their existing behavior. The complete development-worktree gate passed; its `dirty=true` classification is explicit and is not a clean release-tag claim. Durable remote execution intentionally remains disconnected from the Server composition root until Phase 2 persistence and Phase 4 continuation exist.

Phase 2 makes PostgreSQL authoritative for remote Task correlation and polling without claiming Workflow continuation. Real infrastructure evidence proves admission uniqueness, execution-mode preservation, concurrent claim CAS, queue-client restart, Provider-unreachable backoff/recovery, terminal-control idempotency and stale-Provider audit-only behavior. The Server now composes polling/reconciliation only behind the explicit isolated V1.1 safety latch, shares the existing context serializer, and leaves ordinary interrupted Workflow recovery unchanged. Phase 4 still owns production admission from Workflow execution and durable continuation consumption.

Phase 3 makes availability a guarded, append-only planning and pre-invocation evidence flow without changing Workflow runtime authority. Strict DSL validation, immutable scheduled-time resolution, exact-argument refresh, stale-confirmation rejection and adapter-only wire mapping are covered by unit, contract, real PostgreSQL integration and vertical E2E tests. Forecasts remain non-authoritative, and SDAR neither reserves resources nor synthesizes Provider business timeouts. Phase 4 still owns remote-handle admission and continuation; Phase 5 owns Provider business-result mapping.

Phase 4 makes a bounded PostgreSQL frontier snapshot the sole durable continuation authority. A remote handle ends the active LangGraph invocation; terminal controls are claimed once, validated against immutable Task/Goal/plan/instance/node-run authority, and injected into a fresh LangGraph `Command.goto` invocation without replaying START or completed side effects. Redis carries only one-attempt control references, child Skill Workflows continue before their parents, and Goal Patch/cancellation invalidate both mapped and not-yet-mapped bindings for the old Goal version. Phase 5 still owns `input_required`, `tasks/update`, cancellation acknowledgement/uncertainty and complete Provider business-result mapping.

Phase 5 reuses the existing Task input boundary without entering Goal formulation or Workflow planning. PostgreSQL binds each input request to the exact remote revision/result hash/node run, validates form elicitation answers, records `tasks/update` acknowledgement or uncertainty and resumes authoritative polling; identical Provider echoes are idempotent while later revisions support multiple rounds. Local Task/Goal cancellation creates a durable cooperative request but keeps Provider status separate through protocol acknowledgement, uncertainty and a later `tasks/get` terminal observation. Completed business errors are bounded domain data with stable reason/retry/partial/alternative evidence and use the existing LangGraph error-handler path; SDAR never synthesizes Provider timing outcomes. Phase 6 still owns management/Console completion, all 16 composed MCP Tasks acceptance scenarios, demos and final publication.
